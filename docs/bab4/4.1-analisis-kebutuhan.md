# BAB IV ANALISIS DAN PERANCANGAN SISTEM USULAN

## 4.1 Analisis Kelayakan Sistem

Analisis kelayakan sistem dilakukan untuk memastikan modul rekomendasi yang diusulkan dapat diimplementasikan pada aplikasi KOSKITA yang telah beroperasi, ditinjau dari tiga aspek berikut.

**Kelayakan Teknis.** Modul rekomendasi diimplementasikan sebagai penambahan pada backend Laravel yang sudah menjadi bagian dari arsitektur KOSKITA (Subbab 2.9.2), sehingga tidak memerlukan perubahan infrastruktur baru. Algoritma hybrid filtering (cosine similarity, CB, CF berbasis memori) dapat dihitung langsung tanpa pustaka pembelajaran mesin tambahan (Subbab 2.2.2), sehingga sesuai dengan skala data prototipe dan sumber daya komputasi yang tersedia.

**Kelayakan Operasional.** Modul rekomendasi tidak mengubah alur kerja operasional KOSKITA yang sudah berjalan (pencarian, pemesanan, pembayaran, komunikasi, manajemen properti, pembukuan) sebagaimana dijelaskan pada Subbab 3.1 — modul ini murni bersifat aditif, menyisipkan langkah "lihat rekomendasi personal" pada alur pencarian kos, tanpa mengganggu peran Backend Developer, UI/UX Designer, Customer Support, dan Marketing pada struktur organisasi (Gambar 3.1).

**Kelayakan Ekonomis.** Karena seluruh komponen (Laravel, Flutter, MySQL) bersifat sumber terbuka dan sudah menjadi bagian dari tumpukan teknologi KOSKITA yang ada, pengembangan modul ini tidak menimbulkan biaya lisensi tambahan.

## 4.2 Tahap Analisis

### 4.2.1 Analisis Kebutuhan Fungsional

Kebutuhan fungsional dirumuskan berdasarkan Perumusan Masalah (Subbab 1.2) dan Pembatasan Masalah (Subbab 1.3), mencakup seluruh fungsi yang harus disediakan modul rekomendasi kos KOSKITA.

| ID | Kebutuhan Fungsional |
|---|---|
| KF-01 | Sistem harus dapat menerima pendaftaran akun baru dan proses masuk (login) bagi calon penyewa. |
| KF-02 | Sistem harus dapat menerima dan menyimpan data profil preferensi pengguna, mencakup status mahasiswa/pekerja, gender, rentang anggaran, lokasi preferensi, dan status tinggal (sesuai Pembatasan Masalah poin 5). |
| KF-03 | Sistem harus dapat menentukan status pengguna (cold-start atau warm-start) berdasarkan ada tidaknya riwayat interaksi ber-rating milik pengguna tersebut. |
| KF-04 | Sistem harus dapat menghitung skor kecocokan Content-Based Filtering antara profil pengguna dan atribut tiap kos menggunakan cosine similarity. |
| KF-05 | Sistem harus dapat menghitung skor kecocokan Collaborative Filtering berbasis memori dari matriks interaksi pengguna, khusus untuk pengguna berstatus warm-start. |
| KF-06 | Sistem harus dapat menggabungkan Skor_CB dan Skor_CF menjadi Skor_hybrid menggunakan strategi switching hybrid berkomponen weighted (Subbab 2.2.3), dengan alpha = 1 otomatis pada kondisi cold-start. |
| KF-07 | Sistem harus dapat menampilkan daftar Top-N kos terurut berdasarkan Skor_hybrid, beserta alasan kecocokan tiap kos (mis. kesesuaian budget, fasilitas). |
| KF-08 | Sistem harus dapat menampilkan detail atribut kos (harga, lokasi, jarak ke kampus, tipe kos, fasilitas, dan foto) kepada pengguna. |
| KF-09 | Sistem harus dapat mencatat interaksi pengguna (rating, klik) terhadap kos, untuk memperkaya data Collaborative Filtering pada perhitungan rekomendasi berikutnya. |
| KF-10 | Sistem harus dapat memungkinkan admin mengelola (menambah, mengubah, menghapus) data kos serta data master fasilitas dan aturan yang menjadi sumber atribut bagi modul rekomendasi. |
| KF-11 | Sistem harus dapat menampilkan kepada admin rincian skor Content-Based, Collaborative Filtering, dan hybrid untuk pengguna tertentu, guna mendukung transparansi dan pengujian algoritma. |

### 4.2.2 Analisis Kebutuhan Nonfungsional

| ID | Aspek | Kebutuhan Nonfungsional |
|---|---|---|
| KNF-01 | Usability | Antarmuka prototipe harus mencapai skor System Usability Scale (SUS) di atas 68 (kategori "Good" ke atas menurut Bangor et al., Subbab 2.5) berdasarkan penilaian responden. |
| KNF-02 | Performance | Sistem harus menghasilkan daftar rekomendasi dalam waktu respons yang wajar untuk skala data prototipe, tanpa membebani perangkat pengguna dengan komputasi (arsitektur thin-client, Subbab 2.9.1 & 2.9.9 — seluruh perhitungan berjalan di backend). |
| KNF-03 | Security | Kredensial dan data interaksi antarpengguna tidak pernah diproses atau dikirim ke sisi klien; autentikasi REST API menggunakan Laravel Sanctum (Subbab 2.9.3). |
| KNF-04 | Reliability/Accuracy | Model hybrid harus menunjukkan performa (Precision@K, Recall@K, NDCG, MAP) yang setara atau lebih baik dibandingkan baseline popularitas, Content-Based murni, dan Collaborative Filtering murni, pada skenario warm-start maupun cold-start (Subbab 2.5, menjawab Perumusan Masalah poin 3). |
| KNF-05 | Portability | Aplikasi harus dapat berjalan pada platform Android dan iOS dari satu basis kode Flutter (Subbab 2.9.1). |
| KNF-06 | Maintainability | Pemisahan modul ContentBasedFilter, CollaborativeFilter, dan SwitchingWeightedCombiner (Subbab 2.9.9) harus memungkinkan tiap komponen algoritma diuji dan dikembangkan secara independen tanpa saling mengganggu. |
